# BGM 종료 재현 차이

과거 `p03-inchat-host-clock/attempt-05`는 실제 종료 코드 0에서 Ogg 관련 객체 4개와 리소스 2개 누수를 기록했다. 신규 `attempt-05-multi-legacy`는 BGM 실제 재생 4/4와 호스트 기능 4/4를 확인했고 실제 종료 코드 0, 잔여 프로세스 0, 누수 진단 0을 기록했다.

두 실행의 프로젝트 입력 매니페스트를 상대 경로로 맞춰 비교했다. 공통 2,750개 경로의 크기와 SHA-256은 모두 일치했다. 과거에만 `.gdignore`와 `host_clock_probe.gd`, 신규에만 `multi_host_probe.gd`가 있다. 실제 실행된 스크립트는 각 시도의 `project` 아래 스냅샷을 기준으로 비교했다.

| 항목 | 과거 누수 실행 | 신규 정상 종료 |
| --- | --- | --- |
| 플레이어 정리 | 플레이어마다 finished 연결을 해제하고 stop 직후 stream을 null로 설정 | 모든 플레이어 연결 해제와 stop 후 별도 루프에서 모든 stream을 null로 설정 |
| 참조 수명 | 반복 중의 플레이어 변수와 기존 UiSound 소유 참조 | 플레이어 배열과 music·main·aux 지역 참조를 retire 반환까지 유지 |
| 관측 시점 | 별도 재생 관측 및 정리 중간 이벤트 없음 | disable 직전 재생 상태와 정리 중간의 tree/clock 상태 관측 및 출력 |
| tree·모듈 정리 | host remove/free 후 이전 sim의 모듈 참조 해제 | 같은 순서로 host와 모듈 정리 |
| 프레임 대기 | 4개 host 정리 후 최종 250ms | 같은 최종 250ms. 분기와 retire 호출에 await 문법이 추가됐고 legacy에서 중간 frame/timer 분기가 실행되지 않았음 |

분리 가설은 동일 호출 내에서 다른 플레이어의 stop이 앞선 플레이어의 stream 해제보다 먼저 수행되는 순서가 결과에 영향을 준다는 것이다. 신규 05의 참조 수명, 관측 출력, 런타임 및 입력을 유지한 채 배치 정리만 플레이어별 stop→clear 순서로 바꾸면 이 가설을 좁힐 수 있다. 관측은 양쪽에서 같은 위치에 남기고, stop→clear 사이 대기와 추가 출력을 넣지 않는다. 기존 05를 대조로 사용하더라도 단회 관측이므로 과거 누수의 원인이나 생산 수정 효과까지 확정할 수 없다. 재현 실패도 가설의 일반적인 반증은 아니다.

기존 승인 계획의 06 ordered 대조 조건은 충족되지 않았다. 신규 K6는 5/6 사용 상태다. 위 가설은 향후 사전등록과 독립 수용이 필요한 제안으로 남긴다.
