# PC0 도구 실패 읽기 전용 조사

판정: PC0 두 회 소진, 제품 GUI 미검증. run-02의 장애는 **최초 창 조회/캡처 경로에서 응답이 끝나지 않은 현상**까지 확인되며 구체 원인은 미상이다. 제품 재실행, 창 활성화, 입력, CUA 호출 및 프로세스 종료를 하지 않았다. 이 메모는 실행 승인이나 추가 예산이 아니다.

## 근거와 한계

- `REVIEW-PC0-RUN-01-INDEPENDENT.md`: 첫 실행은 import의 `active != 1` 가드에서 중단됐고 추가 멤버 식별은 없었다. `run-02/import.os.tsv`는 root exit 0, 보유한 두 member cleanup, Job active 0을 기록한다. 따라서 첫 가드가 두 번째 import의 동일 장애로 반복됐다는 근거는 없다. 이것이 모든 자손의 생애를 증명하는 것은 아니다.
- `run-02/product.os.tsv`: PID 10612가 소유 Job에서 시작됐고 창 표본은 소유 HWND 722278, foreground 526476으로 다르다. brief 180초 timeout 후 소유 Job 종료 요청, root signal/exit 125, active 0이 기록됐다. `product.log`는 초기 anchor/빈 consume만 있다. 정상 종료나 전투 진입 증거는 아니다. 화면과 액션 파일은 없다.
- `REVIEW-PC0-RUN-02-INDEPENDENT.md`와 운영자 인계의 약 710초 대기는 최초 CUA 창 조회/캡처를 묶은 설명이다. 호출별 시작/종료·오류가 남아 있지 않아 get_window, 캡처, 전달, 렌더링, 세션 중 어느 곳에서 막혔는지 분리할 수 없다. 감독기 종료 이후 상위 작업자의 도구 중단은 사용자 ESC가 아니다. 기록된 무입력은 인계와 산출물 부재에 근거하며 모든 OS 입력의 부재를 입증하지 않는다. 비전경 자체가 정체 원인이라는 인과도 입증되지 않았다.

## 도구 계약에서 발견한 공백

- 현재 노출된 `mcp__cua_repl`은 `cua.getState()` / `cua.getApp()` 등으로 시작해 반환 문서에 따라 조작하는 인터페이스다. 별도 설치된 `computer-use` skill의 `@oai/sky` API와 동일하다고 가정할 수 없다. 해당 skill `docs/guidance.md`/`api.md`는 `list_windows`로 반환된 정확히 하나의 창을 선택하고 반환 객체를 사용하며, `Window.id`는 opaque라고 명시한다. 따라서 native HWND를 `sky.get_window` ID로 임의 변환하거나 제목만으로 소유를 증명할 수 없다. 실제 사용 가능한 인터페이스의 문서화된 식별 매핑이 없으면 교차 확인 불가능으로 중단한다.
- skill 문서는 `get_window_state` 캡처를 자동 표시하고 단순 열람을 위한 payload 저장·재처리를 금한다. 기존 `prepared-pc0-owned-v3/EXECUTION-CONTRACT.md`의 모든 전후 사진 파일과 SHA 요구가 현재 도구의 지원된 증거 내보내기와 양립하는지는 미검증이다. 실제 사용 인터페이스에서 허용된 지속 증거를 먼저 확인해야 하며 화면 이미지를 임의 추출하거나 기록 없이 합격 처리하지 않는다.
- skill의 복구 지침은 경량 조회 timeout 후 제한 재시도/세션 재설정을 설명하지만 이는 이미 소진된 PC0 실행 예산을 되살리는 권한이 아니다. 또한 도구 요청을 외부에서 시간 제한했을 때 실제 요청이 취소되는지 문서상 확인되지 않는다. `Promise.race`만으로 미완료 호출을 취소했다고 가정하거나 병렬 입력으로 넘어가면 안 된다.
- skill의 입력 함수는 대상을 자동 활성화할 수 있다. 기존 계약의 입력 직전 foreground 일치 조건은 첫 입력 전에 별도의 명시적이고 허용된 activation과 이후 재관측을 필요로 한다. 그 자체로 입력을 허가하지 않는다. 현재 CUA의 실제 활성화 동작은 해당 인터페이스 문서 확인이 필요하다.

## 다음 범위 제안 — 설계와 독립 심사만

1. PC0과 분리된 **도구 적합성 검토**로 한정한다. 우선 실제 `cua_repl` 반환 문서에서 창 선택·유일성·native 식별 연계·캡처의 지속 증거·호출 timeout/cancel·종료 후 미완료 요청의 처리 가능 여부를 확인한다. 소유 창과 안전한 로그 기준을 문서화할 수 없다면 자동 GUI 경로는 중단한다. 관련 CUA 호출을 이 조사에서 실행하지 않았다.
2. 필요한 경우 독립 심사된 별도 짧은 비제품 진단을 새로 명세할 수 있다. 단, 제품이나 Godot을 시작하지 않고 임의 사용자 창을 조작하지 않으며, 현재 소진된 PC0 또는 이전 Python K=3을 새 이름으로 재시도하지 않는다. 호출 단계별 시작/종료/오류 및 독립 monotonic deadline을 남긴다. 정체가 발생하면 요청의 실제 취소 확인 전 추가 호출·입력을 금지한다. 진단 예산과 중단 조건을 별도 확정하기 전 실행하지 않는다.
3. 적합성 확인이 불가능하면 사람의 실제 PC 플레이/관찰을 대안으로 검토한다. 사람이 직접 화면과 입력을 수행하고 소유 프로세스·격리·시간 및 결과 증거를 남길 수 있는지 먼저 명세하고 독립 심사한다. 자동 trace만으로 실제 화면/입력 수용을 대체하지 않는다. 이 대안도 새 제품 실행 허가가 아니다.
4. 장래 실행 시에는 사전 할당된 소유 Job 및 보유 HANDLE만 정리하고 identity/멤버십 확인 실패, 중복 창, 미확인 foreground, stale 관측, 캡처/입력 응답 불명 또는 deadline에 즉시 중단한다. 감독기는 CUA 세션과 독립해 소유 Job만 종료하고 root signal, 관측 member signal, active 0 및 기록 flush를 각각 남긴다. 이름 검색 kill, 기존 사용자 창 종료, PID/HWND 재사용 추정은 금지한다. 로그는 완전한 외부 입력 배제를 증명하지 않는다.

기존 원본/캐시, P03 및 동시 작업을 변경하지 않았고 기존 예산과 두 실패 증거를 유지한다.
