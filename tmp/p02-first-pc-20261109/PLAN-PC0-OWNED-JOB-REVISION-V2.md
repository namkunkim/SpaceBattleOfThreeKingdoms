# PC0 재개 스펙 · Job 소유와 이미지 확인 분리

2026-11-09. [run01 독립 판정](REVIEW-PC0-RUN-01-INDEPENDENT.md)을 기준으로 명세에 복귀한다. 제품은 미완료다. 독립 수용 전 구현·실행하지 않는다.

## 이력과 유한 시도

run01의 격리 probe는 exit 0·Job active 0이었다. HEAD 프로젝트 import는 같은 일반 Godot exe를 실행했지만 own Job active가 1과 다른 순간 감독기가 중단했다. cleanup active 0만 있으며 import root exit와 추가 member PID/image가 없다. 제품 GUI·입력·자연 종료·5-a는 0회다. 부분 cache/lock과 원문을 그대로 보존한다. 이전 Python-only K3는 Python/console broker/payload의 전역 프로세스 조회 및 소유 Job member를 식별·정리하려던 별도 검증이고, run01은 다른 대상·launcher 및 이미 소유한 Job의 단일 member 가드 실패다. 둘은 불명 member의 식별·수명 증거가 부족하다는 점을 공유한다. Python K3 소진과 여덟째 P02 K1~K5·남은 K6·21행은 보존한다.

PC0 run01은 기존 V2/V3 상한 2회 중 1회(1/2)를 사용했다. 남은 것은 실측한 감독기 단일 member 가드를 국소 수정하고 개정 스펙과 실제 runner/manifest를 각각 독립 수용한 뒤 검토 가능한 run02 한 회(2/2)다. 자동 재시도하지 않는다. 격리 probe를 포함한 최초 엔진 생성 요청부터 회차를 센다. 동일 실패나 새로운 실패가 발생해도 원문을 보존하고 이 실행 계열을 닫는다. 별도 진단 실행으로 상한을 우회하지 않는다.

## 변경의 핵심

- **신뢰할 실행과 GUI 대상.** V3 준비물의 일반 Godot GUI exe를 절대 경로, argv/cwd/전용 env, 고정 SHA AB1824F85BFD8E0E4128182C000C4003A3E042245B2967848D089B2A04B22424로 검증한다. suspended 생성의 정확한 process/primary-thread HANDLE을 보관하고 이미지·생성시각·전용 Job membership 확인 후 한 번 resume한다. 경로/해시 또는 assign/membership 실패 시 resume하지 않고 정확히 자신이 만든 suspended root만 정리한다. 실제 입력 대상은 승인된 root의 실제 HWND로 제한한다. 실행 파일 경로에서 읽은 파일 SHA는 적재된 메모리 전체의 불변을 입증하지 않는다. 액션마다 foreground, owner PID·creation time·image SHA·Job membership과 client rect를 확인한다. 다른 member가 만든 GUI는 입력 대상으로 채택하지 않는다.
- **소유와 정리.** 각 단계의 unnamed 전용 Job에 kill-on-close, breakaway 및 silent breakaway 미설정, 비상속 Job HANDLE과 명시한 출력 HANDLE만 상속한다. own Job의 child count 변화는 자체 실패 조건에서 제거한다. 이 멤버십은 수명과 정리 범위를 정하며 임의 child 바이너리의 신뢰나 보안 sandbox를 입증하지 않는다. 정확한 반환 root HANDLE은 member snapshot과 독립적으로 유지한다. Job 단위 PID 목록을 시작·주기·종료에서 조회하고 별도 member notification은 보조 관측에 쓴다. 각 관측 member의 PID, 관측시각, own Job membership, 가능하면 creation time·image 경로와 보관 HANDLE을 기록하고 접근 가능한 이미지 SHA와 exit를 추가한다. 부모 정보는 가능한 경우 보조 자료다. PID 재사용/빠른 종료/권한 거부는 미확인으로 남기며 정상 식별로 바꾸지 않는다. notification 누락, race, bounded 목록 버퍼 재시도를 고려하며 membership/accounting 자체의 모순이나 정리 실패는 실행 실패다. own Job에 속하고 image만 미확인인 member는 감사 한계다. basename만으로 승인하거나 입력을 보내지 않는다. 전역 프로세스 검색·종료·assign을 금지한다.
- **실제 종료.** root HANDLE signaled와 실제 exit 채취, own Job active 0과 보관 member HANDLE 모두 signaled, 로그 flush를 각각 남긴다. root exit 0만으로 단계 성공 처리하지 않는다. active 자손은 기존 단계 deadline 안에서 최대 10초 drain한다. 초과·예외·abort에서는 자신의 Job만 종료하고 동일 종료 증거와 root 강제 종료 코드를 별도 남긴다. cleanup 관측 상한 10초를 감독기 전체 시간에 별도 표시한다. kill-on-close는 감독기 장애의 안전 경계이며 active 0/exit 증거를 대신하지 않는다. 불명 member의 개별 exit를 추정하지 않는다.
- **실행 폐쇄와 제품.** 격리 probe→fresh import→제품 Windows는 직렬이며 각각 다른 Job을 사용한다. 기존 1,470개 source manifest·terminal overlay/oracle과 동등한 입력을 확인하고, run01 cache/lock 또는 원본 cache를 가져오지 않는다. run-02의 새 전용 APPDATA/LOCALAPPDATA/cache/log/screenshot만 사용한다. run-01의 .recovery_mode_lock 및 부분 import를 보존한다. 원본 HEAD/index·P03 +9·worker와 원본 user/cache, 격리 source closure는 전후 해시로 대조한다. 동시 작업 drift는 기록하고 복원·stage하지 않으며 관련 입력이 바뀌면 실행을 멈추고 재심한다. import 300초, 제품 1,920초와 V3 하위 단계 상한을 유지한다. import exit와 cache 검증 전 제품 launch 금지. 정상 GUI 조작과 자연 종결·결산 기준은 V3 계약을 유지한다.
- **독립 심사.** 준비 diff는 launcher의 Job·계측·감독 경계와 로그만 변경한다. 5-a 합성 반례는 root 정상·실패, drain, enum race/unknown image·PID reuse, timeout·종료 실패, assign 실패에서 resume 없음, 다른 foreground/HWND에 입력 없음이다. 합성 반례와 실제 Win32 결과는 구분한다. 준비물별 SHA·argv·deadline·stage/exit 포맷·실패 장부를 묶어 별도 실행 심사를 받는다. 이후 독립 5-b가 실제 member/exit·정리·보호 로그와 V3 플레이 근거를 검증한다.
