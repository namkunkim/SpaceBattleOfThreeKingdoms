# 첫 PC 작전 · 기존 직접 출전 경로 확인 및 최소 연결 계획

2026-11-09. 기준은 SESSION-REQUIREMENTS-CHECKLIST-20261031.md §0의 사용자 승인이다. 1단계 첫 플레이 → 2단계 같은 규칙 저장·재개 → 별도 확장 순서다. 이전 P02 여덟째 조각과 21행/K6, K1~K5 결과 및 남은 1회는 그대로 별도 추적한다.

## 발견과 선택

- project.godot:14의 기본 씬은 FleetBattle3D다. 실제 캠페인 입구는 천하 지도에서 기존 적벽 카드를 열어 직접 지휘 출전하는 한 경로다. view/world/world_map_screen.gd:540/550/588은 BattleBrief 생성과 direct 분기를, scripts/world_link.gd:18/26/32는 장면 전환과 결과 한 번 인수를 소유한다.
- scripts/FleetBattle3D.gd:176/270/316은 후보 준비와 성공 게시를 이미 분리한다. 동일 sim에서 초기 배치/직접 지휘·입력과 명령(584), tick 진행(478), 진영 0 사건 소비(565), 종료 화면(473)이 연결된다. 433~436에서 종결 sim의 BattleOutcome을 만들어 천하로 넘기고, 지도는 결과를 한 번 인수(99)하여 표시(622)한다. 기존 이탈은 결과 없는 복귀다. scripts/world/battle_outcome.gd:26~69는 기존 승패/제한 승리·종결 시간·손실을 표현한다. 이 세 종류로 새 작전의 목표·철수·실패를 구별할 수 없다.
- legacy 연결은 코드와 수용된 지정 실행에서 실재한다. P02-LEGACY-OUTCOME-RESULT의 실제 적벽 직접 출전/서막 건너뛰기/자동 편성/결과 버튼은 종료를 주입한 통합 관측이다. K6 재개 인계와 이전 WorldLink clean-user 서막 단언 실패도 유지한다. P03 host-clock 독립 마감은 음악 제외 격리 호스트의 실제 첫 프레임과 invalid profile 재초기화 보존을 확인했다. 기본 PC 전체 플레이나 자연 종료로 확대하지 않는다.
- 제한 P02 runtime adapter는 explicit fresh CLI 스키마이고 core/battle/operation_private_state.gd:86/103에서 증원과 지원 밖 모듈을 거부한다. P03 active 인계는 실제 자동 편성의 DecisionBoard를 보았고 제한 adapter는 비어 있지 않은 scenario를 거부한다. 여덟째 후보 helper는 legacy BattleSim 생성 일부의 공통화다. 이 helper의 수용 여부는 첫 PC 통합 연결에 기술적 선행조건이 아니다. 게임 프로필에서 증원/모듈 제거, private sim 직접 대입, CLI fixture를 제품 우회 입구로 쓰는 방식을 금지한다.
- 즉시 수행할 가장 작은 조각은 **기존 천하 직접 출전의 PC 기준선과 실제 캠페인 결과 연결 경계 확인**이다. 현재 구현을 먼저 실측해 고장만 고친다. 최소 신규 연결의 후보는 같은 진입/화면 경로에서 P05/P07 승인 작전 정의로 준비하고 그 작전의 동일 권위 상태를 진행시킨 뒤 확정 결산을 지도에 한 번 전달하는 opt-in 분기다. P07 정책·실제 데이터와 P03 최소 권위 계약 없이 새 결과·이벤트·증원 성공을 가정하거나 임시 제품 모델을 만들지 않는다. 기존 직접 출전이 실측을 통과하면 이 조각은 증거로 종결하고 다음 blocker는 P07/P03 계약·런타임으로 넘긴다.

PC0 Windows 기준선은 단일 대상 창 HWND/PID 및 전경 대조, 화면 관측과 명령·제품 사건을 연결한다. 자동 PC 입력과 사람 플레이는 구분하고 제3자 입력의 완전 배제는 주장하지 않는다. 실제 종료까지 플레이하지 못한 제어 fixture는 별도 smoke로 남긴다. 약 20분은 게임시계와 실제 경과를 따로 기록하는 비교 가설이다. 반복 시도는 K6과 별개인 새 조각으로, 제품 변경 전 없는 baseline은 실측 한 회와 오류 원인에 한한 한 회만 재시도한다. SCRIPT ERROR·대상 창 이탈·기대 transition 부재는 실패다. 이전 P09 종료 진단은 별도 기록하고 새 진단은 범위와 원인을 드러낸다.

## 소유권과 실행 순서

1. 이 문서에 독립 계획 심사를 받는다. 공유 호스트 변경에 앞서 P03 active/최근 인계를 대조하고 해당 owner와 겹치는 파일과 쓰기 순서를 확인한다. 기준선은 읽기 전용이므로 현행 active private-state hunk를 보존하고 저장·재개 소유권은 2단계로 둔다.
2. 승인된 PC0·PC1 관측 전에 HEAD/index·입력 closure·해시, 실행 argv와 fixture, 독립 기대치, PC 창과 산출물 위치를 고정한다. 실행 캐시와 사용자 데이터는 격리한다. 결과가 통과하면 legacy 공통화나 기존 진입점 수정은 작업 범위에서 빠진다.
3. 확인된 장애가 있으면 해당 호출 경계에만 수정계획·정확한 허용 hunk를 별도 독립 심사한다. 후보 파일은 scripts/FleetBattle3D.gd, view/world/world_map_screen.gd, scripts/world_link.gd, scripts/world/battle_outcome.gd의 확인된 접점이다. 이 목록은 쓰기 허가가 아니다. P03 권위 코드와 P05/P07 데이터는 해당 owner가 맡는다.
4. 신규 연결 전 계약은 P05 승인 좌표/접근 데이터, P07 최소 정책/시한/비용, P03 단일 권위 sim·clock·명령/투영/사건/terminal, PC 호스트 prepare/publish와 결과 단일 전달이다. 현재 P07 계획에 적힌 구 K6 의존은 §0 사용자 승인과 실질 코드 의존을 적용해 독립 재심한다. K6 자체의 행이나 한도는 변경하지 않는다.
5. 5-a는 선택한 조각의 결정적 oracle과 관련 회귀, 5-b는 별도 비Astra 독립 심사, 6은 계획·원문 로그·인수 범위/편차·후속 기록이다. 현재 읽기 조사만 수행했고 K6, 제품, PC 기준선은 실행하지 않았다. 전체 P02/P03 및 저장 스키마 판정은 미완료/UNCLASSIFIED를 유지한다.
