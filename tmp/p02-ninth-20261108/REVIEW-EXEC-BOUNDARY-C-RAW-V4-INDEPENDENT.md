현재 도구의 yield/session·cell terminate와 전달 output token cap은 소유 process tree의 hard deadline, raw disk cap 및 retained HANDLE drain receipt로 정의돼 있지 않다. 이를 K6의 별도 Job 계약으로 자동 대체하지 않는 판정은 적절하다. 실제 관리형 환경에서 제공되는 기능을 추가 조사할 수 있으나 미제공 기능을 주장하지 않는다. 동시에 모든 제품 작업에 OS read-deny를 자체 의무로 추가하지 않는다. 실제 필요한 소유·정리, 독립 snapshot·원본 보호와 검증 가능한 한계를 구분한다.

[Windows Job-list/handle-list 속성](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)은 유한한 direct-native 설계의 근거다. 이는 이전 Python broker와 다른 창출·할당 구조이나 Job ownership·종료라는 공통 목표의 실패 이력을 지우지 않는다. 이미 Python K=3이 소진된 상황에서 새 `K=1`을 별도의 이름으로 선언하는 것만으로 추가 실제 시험 권한이나 기존 재시도 한도의 자동 재설정을 정당화할 수 없다. 스펙 복귀 후 무엇이 이전 실패의 원인을 해결하는지, 사용자 목표에 필요한 실질적으로 다른 계약과 전체 실패 이력·유한 상한·최소 normal/timeout 검증의 관계를 독립적으로 판단해야 한다. 새 시험이 사실상 같은 미해결 ownership gate를 우회하는 것이라면 멈춘다. 실제 binary/compiler/launcher 또는 timeout/cleanup은 아직 없다. 본 심사는 추가 실행을 허용하지 않는다.

C v4는 각 packet의 raw bytes에 Godot HashingContext를 적용하고 별도 adapter가 hex decode 후 Python SHA를 계산한다. 텍스트 hex hash와 raw byte hash를 구분한 수정은 코드 및 합성 4반례 로그와 일치한다. `mono_usec`×1000은 단위를 ns로 표현할 뿐 원래 microsecond 정밀도를 높이지 않으며 동일 시각은 ordinal로 구분한다. `verify_lane`은 기존 whole-lane 검증 후 20 cases×5 call receipts를 v9에 넘기는 정적 경로가 있다. 이는 실제 100/200회가 실행됐다는 뜻이 아니다. 합성 테스트는 raw SHA만 다루며 전체 5,080행→v9 end-to-end 통과·양 lane pairing을 입증하지 않는다. `verify_lane`의 승인 pin은 호출자가 공급하므로 독립 승인 pin과 process/run·raw SHA를 최종 runner에서 강제해야 한다. Geometry, v7 causal chain, alias/detach/suffix, 실제 packet decoder/engine parser 및 관측량·deadline은 미검증이다.

다음 유한 작업은 direct launcher의 정확한 fail-closed contract와 정적 검토, C 동일 raw의 독립 pin/geometry/causal/alias 통합 및 실제 21행 manifest 완성이다. 실제 시험은 기존 K3 이력을 반영한 스펙·예산과 소유/정리 경계의 별도 독립 심사 후에만 검토한다. Sky 귀속·175/320 및 P03 활성 변경 보호를 유지하고, HEAD lane의 P03 결합 미검증을 명시한다. K6은 한 회 남았다.
