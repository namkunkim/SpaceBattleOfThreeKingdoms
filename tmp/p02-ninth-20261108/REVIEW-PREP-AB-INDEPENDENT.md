# P02 선행 A/B 독립 심사

판정: **정적 인벤토리와 사전 적합성 명세의 초안으로 유용하다. 실행 승인과 제품 통과 판정은 아니다.** `PREP-AB.md` SHA-256 `47570d1ac86347a0929fbb0975edd75160fb0c8d721f30108f95f0d3fa347bd6`, `source-evidence.json` `4dab7e743db784b0b5e599965dffd225bc5a6b8c3620c3d015cbfe39f6b7c9b3`, `inventory.py` `08a6016739e7755f93f28dc9860efc3dbf5cec815fc7a82972124f64a07c1970`를 직접 확인했다. 산출물은 작성 turn 메타데이터의 gpt-6.1-sol을 기록한다. 이 독립 심사 turn의 `nodeRepl.requestMeta`는 **gpt-6.1-terra / low**다. 제품 suite, Godot, OS 입력 및 Job 실험을 이 심사에서 실행하지 않았다.

## 확인과 한계

- 7 suite의 source provenance, HEAD/ZIP/worktree 구분과 V5 14개 명령의 연결은 다음 단계에 쓸 수 있다. 스크립트는 정적 정규식 기반 색인이며 전체 의존성이나 도달 가능성의 증명기가 아니다. 동적 경로·디렉터리·import/cache 및 test overlay까지 별도 고정해야 한다. sampling 전후 일치로 그 사이 불변을 주장하지 않는다.
- worker의 정상 59와 replay의 정상 101은 제시한 정상 분기 기준으로 소스와 양립한다. worker의 `joined` loop 검사는 별도 `failures`에 누적되며 `checks` 59에 포함되지 않는다. replay 두 번째 factory 실패 시 controls 단언이 빠지므로 101만으로 분기 성공을 판정할 수 없다. 정상 경로 기대 순서/labels, 각 early exit 및 running-frame 검사를 각각 분모에 연결하고 하나라도 누락되면 실패시키는 것이 필요하다. 정적 값은 실행 증거가 아니다.
- 나머지 다섯 suite의 fixture 의존 가중식과 행 20/21의 전체 사례·기존 WorldLink clean 단일 실패 허용 원문은 아직 미완성이다. 14행/148, 11,553, 2,202, 20,099 등 과거 출력은 현재 분모 대용이 아니다. 테스트 overlay는 실제 실행될 변형본이므로 원본/변형 SHA 및 diff, 계측 삽입이 결과를 바꾸지 않는다는 검토와 실패·누락·중복 로그를 거부하는 반례가 필요하다.
- Job 세 행은 정상·강제 종료·할당 거부를 분리하고 실제 V5 broker 방식을 맞춘 점이 적절하다. `active_at_join: 0` 리터럴을 독립 관측으로 취급하지 않는 것도 옳다. 제안의 console→GUI 자손 구조가 실제 사용 engine wrapper에서 생기는지는 아직 미측정이며, 생기지 않으면 실제 프로세스 트리를 기록하고 별도 의도적 자손 생성 시험을 구분해야 한다. 실제 nested 거부 환경이 없으면 미검증으로 보고 인위 플래그로 대체하지 않는다.
- GUI 네 행은 창 식별과 입력 귀속을 구분하며 위험을 정확히 남긴다. 제목·PID·foreground·hook·timestamp만으로 Sky 특정 요청의 유일한 원인을 증명하지 못한다. 별도의 검증 가능한 provenance가 없으면 해당 GUI는 보류다. 최소 테스트 창과 관측/합성 시험은 제품 시험보다 범위가 좁지만 전역 hook과 활성화·입력은 사용자 데스크톱에 영향을 줄 수 있으므로 사전 명세에 대상·수집 범위·즉시 해제·실패 시 정리를 적는다. 합성 입력 성공을 OS 실제 사용자 경로로 집계하지 않는다.

## 전진 경로

1. 남은 다섯 suite와 20/21에 대해 **한 번의 유한 대조 작업**으로 fixture별 조건, 필수 assertion ID/순서·동적 반복식·실패 시 누락 조건, 원문 기대 exit 및 WorldLink 허용 실패를 완성한다. 실행 시 dynamic 수량이 달라질 수 있는 것은 입력에서 독립적으로 산정하거나 필수 사건/분기 집합과 상한을 검증하고, 단순 총량만 맞춰 통과시키지 않는다. 원문 fixture/runner/overlay, P03 snapshot의 동일 before/after 선택과 SHA를 고정해 독립 검토한다.
2. 제품 외 적합성의 구체 명령과 최소 격리 프로젝트, 엔진·runner SHA, 독립 process handle 및 cleanup·시간 제한을 확정하고 독립 심사한다. 승인된 범위에서 실제 Job 정상/timeout 관측과 재현 가능한 경우 assign 거부를 수집한다. 해당 실패를 재현할 수 없으면 보류 항목으로 보존한다. GUI는 우선 창 식별/관측 가능성만 평가하고 요청 주체 귀속 방법의 반례를 해소하지 못하면 제품 GUI 인수를 보류한다. 이 결과는 K6의 제품 결과에 합산하지 않는다.
3. 제품 21행에 최종 입력·명령·oracle·실제 버튼 경로·분모·실패 원자성·출력·deadline·소유권을 결합하고 독립 심사 후 K6 한 번을 실행한다. 전체 또는 일부 실행을 추가 시도로 리셋하지 않는다. 실패 시 원문을 보존하며 제품 변경 전 독립 5-b가 필요하다. 현 단계는 실행 가능성을 판단하기 위한 준비이지 K6 시작 허가가 아니다.

기존 K1~K5와 K4 시간초과 실패, K5 GUI 귀속 미확인을 유지한다. P03 9행과 worker 작업 트리 2행은 보호 대상이며 이 심사는 원본 파일을 변경하지 않았다.
